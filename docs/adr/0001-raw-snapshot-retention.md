# 0001 raw_snapshot 보관 정책 — 영구 보관

- 상태: 확정
- 날짜: 2026-10-31
- 담당: 준혁

## 문제

raw_snapshot 은 금감원 API 응답 원문을 날짜·상품군·권역·페이지 단위로 쌓는다. 언제까지 둘지 정해야 한다.

제약
- API 에 날짜 파라미터가 없다 — **지운 날의 원문은 다시 받을 수 없다**
- 정규화·변경 감지 규칙은 계속 바뀐다. 규칙을 고치면 과거 원문으로 다시 돌려 product·rate_history 를 재구성해야 한다
- 용량: 하루 15페이지 약 2.4MB(2026-10-28 실측) → 1년 약 0.9GB. RDS gp3 20GiB(ADR-0006)
- RDS 자동 백업 보존은 1일로 제한된다(ADR-0006)

## 선택지

1. **영구 보관** — 지우지 않는다
2. 기간 보관(예: 90일) 후 삭제 — 정규화 결과만 남긴다
3. 기간 보관 후 S3 로 옮기고 DB 에서 삭제 — 원문은 남기되 DB 는 가볍게

## 결정

1번. raw_snapshot 행은 지우지 않는다. 날마다 그날 원문을 csv.gz·지문으로 S3 에 따로 남긴다(`deploy/ec2/backup.sh`).
DB 용량이 RDS 저장소의 70% 를 넘으면 3번(오래된 행을 S3 에만 두기)을 새 ADR 로 검토한다.

## 근거

- 2번은 되돌릴 수 없다. 원문을 지운 뒤 정규화 버그가 드러나면 그 기간의 이력은 고칠 방법이 없다
- 1년 0.9GB 수준이라 몇 년은 20GiB 안에 들어간다 — 지금 지울 이유가 없다
- 3번은 아카이브·복원 절차가 더 필요하다. 용량 압박이 생기기 전에는 들일 비용이 아니다
- S3 날짜별 백업이 RDS 1일 보존의 빈틈을 메운다. 복구는 `deploy/migrate/import.sql`

## 결과 · 트레이드오프

- 얻은 것: 어떤 날짜든 원문부터 다시 정규화할 수 있다. 수집 버그·규칙 변경에 대한 안전망
- 포기한 것: DB 가 계속 커진다. 권역(여신전문·보험 등)을 늘리면 증가 속도가 바뀌므로 그때 용량을 다시 잰다
- 원문에 개인정보는 없다(상품 공시 데이터) — 보관 기간을 줄여야 할 규제 사유가 없다
